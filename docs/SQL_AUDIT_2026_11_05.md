## F11 : premier doublon d’index retiré

Migration appliquée : `20261105063200_remove_duplicate_transaction_wallet_index.sql`. Le nom de fichier local a été aligné sur la version enregistrée par Supabase après application.

Les deux index `idx_tx_wallet` et `transactions_wallet_id_idx` avaient exactement la même définition : btree non unique sur `public.transactions(wallet_id)`, sans prédicat ni option. Chacun occupait 139 264 octets. Aucun n’était une clé primaire ; aucune contrainte ni dépendance n’imposait de garder la copie retirée. L’index conservé avait 42 316 scans observés, contre 13 pour l’autre ; ces statistiques ne constituent pas un benchmark.

La migration conserve `transactions_wallet_id_idx` et retire seulement `idx_tx_wallet`. Elle vérifie les définitions exactes, la validité, les rôles particuliers et les dépendances ; elle refuse un schéma différent. Pas de CASCADE. Un verrou transactionnel bref empêche une modification concurrente du schéma : attente maximale de deux secondes, commande bornée à cinq secondes. Une seconde exécution ne modifie rien si l’index conservé est toujours conforme. La commande de recréation est documentée dans le fichier.

Validation réelle : migration exécutée deux fois dans une transaction annulée, restauration du doublon vérifiée, puis application et relecture des catalogues. EXPLAIN sur un identifiant wallet synthétique utilise `transactions_wallet_id_idx` (Index Scan, coût estimé 0,28–2,50). Aucune promesse de gain mesuré de latence ; une copie d’index et son entretien lors des écritures sont supprimés. Aucun code applicatif ne référence les noms de ces index.

Les [signalements d’index identiques](https://supabase.com/docs/guides/database/database-linter?lint=0009_duplicate_index) passent de **12 à 11 groupes** après migration ; le groupe wallet traité a disparu. Les index uniques ou liés à des contraintes n’ont pas été retirés.
