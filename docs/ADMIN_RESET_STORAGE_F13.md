# F13 : contrat de réinitialisation administrative, Documents et Storage

Revue statique sur la branche d’audit au commit `20991a15`. Ce document ne définit ni commande, ni migration, ni mécanisme de suppression à activer. Le login et les données des tiers doivent rester intacts.

Elle ne sollicite pas Storage. La [documentation Storage Supabase](https://supabase.com/docs/guides/storage/schema/design) distingue le stockage physique de ses métadonnées et demande de modifier les objets via l’API Storage, pas par SQL.

## Contrat à prouver sur un banc isolé

1. **Avant écriture :** inventaire complet des références dans les deux sens pour le compte fictif, niveau de propriété vérifiable, aucune ambiguïté ni référence de tiers. Sinon, aucune modification. Recenser les colonnes de propriété, FK, contraintes, triggers et politiques de Documents, dossiers, boîte de réception et relations Trip, Transactions, Patrimoine, Travail et connecteur. Exiger une source de schéma versionnée ou exportée sans lignes, pas un accès au compte signalé.
2. **Dans la même transaction SQL :** appliquer uniquement le plan privé vérifié et enregistrer un état durable de nettoyage des objets explicitement ciblés. Si un contrôle différé échoue, ni les modifications ni cet état ne doivent survivre. Ne pas toucher Auth. Si une référence ne peut être classée, ne supprimer ni ligne ni objet.
3. **Après commit, uniquement par API Storage :** les fichiers et le SQL ne partagent pas de transaction ; l’interface doit distinguer le commit SQL d’une fin confirmée du nettoyage. Vérifier l’identité ou l’immuabilité de chaque objet avant d’autoriser une reprise, notamment si un nouvel envoi réutilise une clé. Sans preuve, l’objet reste en attente pour vérification. Pas de purge automatique d’un dossier par préfixe. Un résultat incomplet, un échec de lecture ou une réponse perdue ne prouvent pas l’absence de l’objet.

Tests d’acceptation à construire : annulation SQL sans nettoyage en attente ; référence tierce ou non classable bloquante ; panne après commit mais avant nettoyage ; réponse Storage perdue puis relecture ; fichier remplacé sous la même clé ; plus d’une page d’inventaire ; compte voisin, connexion et nouvelles pièces jointes intacts. Distinguer les modèles de panne synthétiques du vrai service Storage et des SDK/clients plus anciens.

### Preuve partielle : point de contrôle SQL

`scripts/audit-admin-reset/checkpoint.mjs` utilise trois connexions à un PostgreSQL jetable sur loopback, sans opération Storage. Des lignes fictives marquées, un reçu SQL et un objet en attente sont invisibles depuis une seconde connexion avant commit et absents après un échec différé. Après commit, une nouvelle connexion retrouve le reçu et la cible exacte, même sans reprendre la session du demandeur. Le compte voisin est inchangé. Le script prend les mêmes deux paramètres que les autres bancs F13. Il ne teste ni reprise de travail, ni concurrence entre travailleurs, ni identité/version vérifiée dans Storage.
